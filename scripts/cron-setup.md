# Системный cron: автоотмена просроченных заявок на бронирование

## Зачем

`expireStaleBookings()` отменяет заявки, на которые владелец не ответил за 12 часов,
и уведомляет обе стороны (колокольчик + Telegram). Без cron эта логика «ленивая» —
срабатывает только когда кто-то открывает страницу «Мои брони». С системным cron
истечение работает **вообще без посетителей**, каждые 10 минут.

Эндпоинт: `GET /api/cron/expire-bookings` — уже существует в коде и защищён
заголовком `Authorization: Bearer $CRON_SECRET` (без секрета отвечает 401 —
проверено на проде).

## Шаг 1. Сгенерировать секрет (если ещё нет)

На своём компьютере:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Вывод — случайная 64-символьная строка. Это и есть секрет.

## Шаг 2. Добавить секрет в окружение ПРИЛОЖЕНИЯ на сервере

Где именно — зависит от того, как запущено приложение (systemd-сервис, pm2, Docker):

- **systemd**: в файле юнита (обычно `/etc/systemd/system/<имя-сервиса>.service`)
  в секцию `[Service]` строка `Environment=CRON_SECRET=<секрет>`, затем
  `sudo systemctl daemon-reload && sudo systemctl restart <имя-сервиса>`;
- **pm2**: `pm2 set <app>:CRON_SECRET <секрет>` или через `ecosystem.config.js`;
- **Docker**: переменная в `docker-compose.yml` / `docker run -e`.

⚠️ Секрет в `.env` проекта на сервере тоже сработает (Next.js читает его),
если приложение стартует из папки проекта. Уточните у того, кто настраивал деплой.

## Шаг 3. Строка для crontab

На сервере (под пользователем root или тем, от кого работает curl):

```bash
sudo crontab -e
```

Добавить строку (одной строкой, без переносов):

```
*/10 * * * * curl -fsS -H "Authorization: Bearer <СЕКРЕТ>" https://naradare.by/api/cron/expire-bookings >/dev/null 2>&1
```

Разбор по частям:

- `*/10 * * * *` — расписание: каждую 10-ю минуту часа (00, 10, 20, 30, 40, 50).
  Пять полей: минуты, часы, день месяца, месяц, день недели. `*/10` = «каждые 10 минут»;
- `curl -fsS` — флаги: `-f` = «считать HTTP-ошибку (401/500) провалом curl»,
  `-s` = тихий режим, `-S` = но ошибки всё же показывать;
- `-H "Authorization: Bearer <СЕКРЕТ>"` — заголовок, который ждёт эндпоинт;
  `<СЕКРЕТ>` заменить на строку из шага 1 (без кавычек и пробелов);
- `https://naradare.by/api/cron/expire-bookings` — адрес (идём через домен и nginx,
  как обычный посетитель);
- `>/dev/null 2>&1` — выбросить вывод cron'а, чтобы не засорять почту root.
  Для первых запусков лучше УБРАТЬ эту часть — увидите ответ `{"expired":N}` в логах.

## Шаг 4. Проверка

1. Разово выполнить команду curl вручную (без `>/dev/null`):
   ```bash
   curl -fsS -H "Authorization: Bearer <СЕКРЕТ>" https://naradare.by/api/cron/expire-bookings
   ```
   Ожидаемый ответ: `{"expired":0}` (или число реально истёкших заявок).
   Ответ `{"error":"Unauthorized"}` — секрет в curl и в окружении приложения не совпадают;
2. Подождать 10 минут, на сервере посмотреть лог cron:
   ```bash
   grep CRON /var/log/syslog
   ```
   (Debian/Ubuntu; на других дистрибутивах — `journalctl -t CRON`);
3. Создать тестовую заявку и не отвечать на неё 12+ часов — она закроется сама,
   обе стороны получат уведомления (колокольчик + Telegram).

## Почему каждые 10 минут, а не раз в сутки

Окно истечения — 12 часов. Раз в сутки давал бы задержку до 24 часов (заявка
истекла в 14:00, отменится только в 03:00 ночи). Каждые 10 минут — задержка не
больше 10 минут, а нагрузка мизерная: один GET-запрос, который при пустой таблице
делает один SELECT и завершается.

## Безопасность

- Секрет передаётся только по HTTPS — перехват невозможен;
- Без секрета эндпоинт отвечает 401 (проверено) — чужие не дёргают;
- Даже если дёрнут: операция идемпотентна — повторный запуск по уже
отменённым заявкам ничего не меняет (фильтр `status = 'new'` их больше не находит).
